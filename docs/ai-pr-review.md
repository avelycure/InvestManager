# AI-ревью pull request

`.github/workflows/ai-review.yml` запускает `scripts/ai-review.mjs` при открытии и обновлении PR из ветки этого репозитория. Скрипт получает список файлов и diff, строит эмбеддинги README, документации и подходящих фрагментов исходного кода базовой ветки, находит относящийся к изменениям контекст и отправляет его вместе с diff OpenAI-совместимой модели. Результат появляется в одном комментарии PR. В нём модель должна указывать потенциальные баги, архитектурные проблемы и рекомендации со ссылками `файл:строка`. Вывод модели следует проверять вручную.

## Настройка

1. В GitHub откройте **Settings → Secrets and variables → Actions**.
2. Создайте секрет `AI_REVIEW_API_KEY` с ключом OpenAI-совместимого облачного API. Ключ не сохраняется в репозитории.
3. При необходимости задайте переменные `AI_REVIEW_BASE_URL` и `AI_REVIEW_MODEL`. Значения по умолчанию: `https://api.openai.com/v1` и `gpt-5.4-mini`.
4. Для эмбеддингов по умолчанию используется тот же базовый адрес API и ключ `AI_REVIEW_API_KEY`, модель — `text-embedding-3-small`. Переменные `AI_REVIEW_EMBEDDING_BASE_URL` и `AI_REVIEW_EMBEDDING_MODEL` позволяют выбрать другой OpenAI-совместимый endpoint и модель эмбеддингов. Если endpoint требует другой ключ, понадобится отдельная настройка скрипта: сейчас оба запроса используют один секрет.
5. Откройте PR из ветки этого репозитория. После попадания обновлённого скрипта в базовую ветку новые PR будут получать ревью с эмбеддингами. Пока базовая ветка содержит старую версию скрипта, PR проверяется прежним поиском по словам.

Запуск с fork-репозитория пропускается: GitHub не передаёт секреты такому PR. Черновики также пропускаются до события **Ready for review**. Отсутствие ключа в обычном PR приводит к понятной ошибке задания, а не к фиктивному «успешному» ревью.

## Как работает контекст

На каждом запуске скрипт разбивает отслеживаемые Git файлы базовой ветки на фрагменты. Все подходящие фрагменты `README.md` и `docs/*.md` входят в набор кандидатов; фрагменты кода предварительно отбираются по словам и путям изменённых файлов. Для ограниченного набора кандидатов и запроса из добавленных строк PR запрашиваются эмбеддинги. Сходство векторов вместе с небольшим весом слов и путей определяет, какие выдержки попадут в запрос ревьюера. Ссылка `файл:строка` позволяет проверить источник контекста.

Это временный индекс на время задания GitHub Actions: он строится заново для актуальной базовой ветки и не сохраняется в репозитории. README, документация и отобранные фрагменты кода отправляются провайдеру эмбеддингов. Личное Obsidian-хранилище не читается. Сборочные результаты и `package-lock.json` исключены. Размер diff и контекста ограничен, поэтому крупный PR может получить неполное ревью — в этом случае части diff явно помечены как опущенные. Если endpoint эмбеддингов недоступен или возвращает некорректные данные, задание завершается ошибкой, чтобы не выдавать ревью без заявленного контекста.

Workflow исполняет скрипт из базовой ветки. Коммит PR скачивается только для чтения diff, его код не запускается. Перед публикацией проверяется, что PR не обновился во время анализа. Повторный запуск обновляет предыдущий комментарий бота, не создавая дубликатов.

Проверка локальной логики: `node --test scripts/ai-review.test.mjs`.
